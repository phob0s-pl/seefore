## The model as it would be

The check lays each change over the model and reads the result (D2). The answer now keeps
what it read: `laid`, for each change with no error of its own, the records it adds and
updates, whole. The page swaps those into the records of today and takes out what the
change removes. It merges no key itself, so a value on the page is the value the check
judged. A change with an error of its own has no `laid`.

## The list, `/changes/<id>/records`

| Part | What it is |
| --- | --- |
| Sections | One for each list the page has, in this order: Context, Features, Flows, Software, Actors, Connections, Technologies, Owners, Data, Rules. Software holds the five folders of its tab. A list the change does not touch has no section |
| A row | The tile of its kind, the name, and at the right a pill: **Added** in green, **Updated** neutral, **Removed** in red. An added or updated record has its name as it would be; a removed one as it is. A line of context shows its sentence. No count and no other column. The rows of a section stand by name |
| Where a row leads | To the record under the change |
| An input alone | "No records yet." and "This change is an input alone. Write what it adds, updates and removes under `add`, `update` and `remove` in `changes/<id>.yaml`." |
| A change with an error of its own | Its rows are read from its file and are no links, under one line: "`seefore check` finds errors in this change, so its records cannot be opened." |

## A record under a change, `/changes/<change>/records/<folder>/<id>`

The address holds the record's path as the change's file writes it. A path the change does
not touch says "This change does not touch that record.", with the way back to Records.

| Part | What it is |
| --- | --- |
| The sidebar, the top bar | The change's own sidebar, Records current. Beside the arrows and the home button, the way back: the change's name, to Need; "Records", to the list; the record's name |
| The title row | The tile, the name, the pill of its type, the pill of the mark |
| A line under it | An added record has none: its mark says it. Updated: "Updated by this change. This is the record as it would be.", and a link "Open it as it is today". Removed: "Removed by this change. This is the record as it is today.", and a link "Open it in the system" |
| Before and after, on an updated record | One panel, a row for each key the change writes, in the file's order: the key, what it says today, what it will say. A text reads as prose. A list of ids reads as links, one a line, with a small "Removed" or "Added" on one that goes or comes. A key that is taken out says "Taken out"; one that is new has "Nothing" before it. Anything else, as `steps`, `fields` or a selector, reads as the file would hold it |
| Under it | The record's own page, from the model as it would be; for a removed record, from the model of today. For the twelve kinds of Models and for a feature. Its description is left out where the description is a key that changes |
| A flow, a rule, a line of context | No page of their own under a change yet: an added or a removed one shows its keys as written, a row a key |

## The links

**One function decides where a record's link leads: `address` of the catalogue.** A
catalogue made for a change knows the paths the change touches: a touched record's address
is the one above, any other the system's. Every page takes a catalogue and never chooses.
The links that are written by hand today move onto it: the rules and the steps on a
record's page, and the rows of the lists of features, rules and context.
