# D2: The body of a change

Stage D2 of `plan2.md`, in milestone 4. The owner asked on 2026-11-25 for "best yaml
structure for proposal", covering records that are added, deleted and updated: models,
flows and features. The main session and Astra each proposed one apart
(`research/changes/body/`, out of Git), and the owner said: "do with recommendation." Built
by the main session.

**After it** a change is a file in a fifteenth folder, `changes/`. After the three keys of
its input (D1) it says which records it adds, updates and removes. `seefore check` holds the
change against the model, and the model as it would be with the whole check.

## The file

`changes/<id>.yaml`. A record is named by its path, `folder/id`, as its file is, without
`.yaml`.

    name: Settlement from a ledger
    prompt: Settlement broke twice when Commerce changed the orders database. Move it onto a ledger.
    add:
      apps/ledger:
        name: Ledger
        in: boxwick
        kind: service
    update:
      apps/settlement:
        description: Works out what each promoter is owed, from the Ledger's entries alone.
      flows/paying-promoters:
        steps:
          - id: reads-entries
            does: settlement-reads-ledger
          - works-out
          - writes
      rules/commerce-databases-stay-with-commerce:
        debt: null
    remove:
      - connections/settlement-reads-orders

| Key | What it holds | Limit |
| --- | --- | --- |
| `name`, `prompt`, `given` | The input | As in D1 |
| `add` | Each new record under its path, whole, as its own file would hold it | An id that no record has |
| `update` | Under a record's path, only the keys that change, each as it will be. `null` takes a key out | A record that is there, and at least one key |
| `remove` | The paths of the records that go | Records that are there, none twice |

- **A key under `update` is written whole**: a description, a list of ids, a selector.
- **A flow's `steps` is the list as it will be.** A step that stays as it is is named by its
  id alone. A new or changed step is written whole. A step left out is gone.
- **All fourteen folders may be named**, rules and context too. A change names no change.
- **A record is in a change once.** A change with none of the three keys is an input alone.
- **A change's id is its own.** It may be the id of a record, as `ledger` for the change
  that adds the Ledger: a change is no record of the model, and no rule chooses one.

## What the check says

| What is held | Fault | Rule | Class |
| --- | --- | --- | --- |
| The form | A path that is no `folder/id`; a record twice in the change; a record under `add` that its folder's shape refuses; a key under `update` that its kind does not have | `change-path`, `change-twice`, and those of one file (B1) | error |
| Against the model | `add` of an id that a record has; `update` or `remove` of one that no record has, or under another folder; a bare step id that the flow does not have | `change-add-exists`, `change-no-record`, `change-step-unknown` | error |
| Against the model | A key under `update` that is what the record says already; `null` for a key it does not have | `change-no-effect` | warning |
| The model as it would be | Every problem of the whole check that the model does not have today | The rule that found it | As that rule |

- **The model as it would be** is the model with the change laid over it. The same check
  runs on it. A problem it finds is told at the change, at the key at fault where there is
  one, with "With this change, `<path>`:" before it. So a record that is removed while
  something still names it is told, and a rule that the change breaks.
- **Each change is held alone against the model**, and a faulty one stops nothing else.
- **Every change is open.** The key that says a change is decided comes with decisions (D3);
  from then a decided change is history, and only its form is held.

## What is out

- **Applying a change to the files, and showing it on the page**: stages of their own.
- **A saved copy of the model that a change was drafted on.** So an edit to a key that the
  model changed since is silent. **Two open changes on one record**: a warning. Both later.
- **A rename as one word.** It is a remove, an add, and an update of every record that names
  it; the check lists them. A record that changes its kind is the same.
- **Options inside one change.** Three options are three changes; D3 records the choice.
  **A reason on every record, and edits of a flow step by step**: never.

## For the owner to approve

The four choices of the proposal, built as recommended: a path for a record; a bare id for
a step that stays; no saved copy of the model; one key for a decided change, named in D3.
Two more from the build: **a key that changes nothing is a warning**, and **a change's id
is its own**.

## Tests

Ten of the check: a change with a body, and an input alone; the faults of a path; a record
under `add` held by its folder's shape at its own line, and unknown keys under `update`; a
record twice; the faults against the model; the two warnings and an unknown step; what the
model as it would be brings to light; a flow that gains and loses a step; a rule broken and
a debt paid; a faulty change that stops nothing. One of the schema.

## The try

The four changes of the proposal, one by the main session and three by Astra, each in a
copy of its trial model: the check reads each with no problem. With the flow left out of
the first, it tells both steps that still name the removed connections.
