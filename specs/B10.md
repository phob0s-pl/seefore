# B10: Ids that say their kind

Stage B10 of `plan2.md`, in milestone 2, built after D9. The owner asked on 2026-11-25: "why
not stable identifiers: app-gateway, component-kms, data-user?", and decided: `infra-` and
`tech-`; connections have a word too; a rule of the check, with a `rename` command first.
Fable and Astra each planned it apart (`research/naming/`, out of Git). Opus builds.

**After it** every record's id begins with the word of its folder, `seefore check` holds
that, and `seefore rename` changes an id in every place that names it.

## The words

| Folder | Word | Folder | Word |
| --- | --- | --- | --- |
| `people` | `person-` | `owners` | `owner-` |
| `systems` | `system-` | `technologies` | `tech-` |
| `apps` | `app-` | `features` | `feature-` |
| `stores` | `store-` | `flows` | `flow-` |
| `components` | `component-` | `data` | `data-` |
| `connections` | `connection-` | `rules` | `rule-` |
| `infrastructure` | `infra-` | `context` | `context-` |

A change and a review take no word: a change is no record of the model, and a review is named
as its change. A step of a flow and a point of a review are named inside their file.

## The rule

**`id-kind`, an error**: an id begins with the word of its folder, with at least one more
group after it. The folder says the kind, so the folder wins, and the mend is one command.

    apps/monitoring.yaml:1:1: error: The id `monitoring` does not begin with `app-`. An id
    says its kind as its first word, and this file is in `apps/`.
      Mend: Run `seefore rename monitoring app-monitoring`. If it is no app, give it the
      word of what it is, as `tech-monitoring`: that moves the file.

- **The record is still read**, so nothing that names it is told as unknown. A record that
  a change adds is held the same way, at the change.
- **A name that begins with the word** needs it once: a feature "Feature flags" may be
  `feature-flags`. The check never holds an id against a name.
- **`id-twice` goes.** Two folders cannot hold one id once each id says its folder.

## `seefore rename`

    seefore rename <old> <new> [--workdir=<dir>] [--dry-run]
    seefore rename --list=<file> [--workdir=<dir>] [--dry-run]

`<old>` is an id, or `folder/id`. `<new>` is an id, and **its first word says the folder**:
the file moves there. So a component becomes an app by `seefore rename component-kms app-kms`.
A list holds one `old new` on a line, and all its lines are done as one, so `a b` with `b c`
is no clash. It prints each file with what it rewrote; `--dry-run` prints and writes nothing.

| Where an id is written | What `rename` does | A miss is told by |
| --- | --- | --- |
| The file | Moves it to `<folder of the new word>/<new>.yaml`, its text as it was | `id-kind` |
| A part's `in`, `owner`, `technology`; a connection's `from`, `to`, `via`, `technology`; a feature's `touches`, `owner`; a line of context's `system` | Rewrites | `reference-unknown` |
| A flow's `feature`; a step's `does` and `data` | Rewrites. A step's `id`, `reply` and `after` name steps and stay | `reference-unknown` |
| A rule's selectors (`id`, `within`, `owner`, `technology`, `data`, at any depth) and `debt` | Rewrites | `reference-unknown` |
| A change: the keys of `add` and `update`, the items of `remove`, and the fields inside | Rewrites folder and id. An id that only a change adds can be `<old>` | `change-no-record` |
| A review's `about` | Rewrites `folder/id`, and the flow of `flows/<id>#<step>` | Nothing, until D4b |
| Prose | Leaves it, and prints each line where `<old>` stands in backticks | Nothing |

- **Only the id's own characters change** in a file: comments, order and layout stay.
- **A connection that names the renamed end in its own id is renamed with it**, when the
  end's id changes after its word: `connection-puma-caches-in-redis` follows `app-puma` to
  `app-webservice`. It is printed. One whose new id is taken or too long is left, and printed.
- **It refuses, and writes nothing**, when `<old>` names no record, or two, or a change;
  `<new>` is no id, has no folder's word, or is taken; or a file that names `<old>` is no YAML.

## The migration

- **The new id is the word and the old id**, for every record, by rote. So seven of 2,263
  say a word twice (`connection-connection-service-…`), and no id is made anew from a name.
- **It is done by `rename --list`**, with a list written from the folders. The test model by
  the command, the tests' inline models by a builder, and the rule turned on last: an id
  with a word is a good id today, so each test file stays green alone.
- **A model is whole** when the check has no error, each folder holds as many files as
  before, and every address in a review names a record. Prose is not proved. The eight trial
  models are out of Git; the private one is done on this machine, and only counts are said.

Addresses keep their form, as `/models/app-order-api`. The examples in messages and the schema
files follow. `format: 1` stays, and earlier specs stay as written.
