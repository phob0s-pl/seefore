# C2: The format's one change

Stage C2 of `plan3.md`: the format and the check change once, before stage D writes two large
models in them. The owner decided twice. On 2026-11-25 they took the joined verdict of Astra
and a Fable architect on eight rows that the runs of `model` and `flows` had asked for, and
the key `source` was built on a step. On 2026-11-26 they decided that **every link from a
record to the code goes**, to come back "with better understanding how to link with source code".

**After it** no record names a file of the code. The format holds what a person draws: parts,
connections, flows. Five conventions that runs guessed are sentences of the guide.

## What goes

| What | It was | Since |
| --- | --- | --- |
| `source` on an app, a store, a component, a piece of infrastructure | One to three paths of the code that starts or defines the part | A2 |
| `source` on a connection | One to three files where the code of `from` names `to` | B2 |
| `source` on a step | One to three files where the code does the step | This stage: built, and taken out again |
| The warnings `source-gone` and `source-folder` | A path that is not there, or is a folder | A2, B2 |
| The check's look at the code's folder | The check reads the model's files and nothing else now | A2 |
| The list's last column; the row "Source" on a record's page; the line in a step's bar | | A2, B2, this stage |

- With no problem the check says: "No problem: the keys are in form, and every id that is
  named is there."
- **A record that still bears the key** is refused as any key that is not its kind's:
  "`source` is not a key of an app. Its keys are …". No model outside this project has one,
  and no trial model does. The models that the runs of B and C wrote do, and stay as research.

## What stays: the rule of evidence, in the skills

The rule was never the key. It is a rule of the session, and both skills keep it:

| Skill | Its rule | Where the proof is now |
| --- | --- | --- |
| `model` | An app is what a file starts. A connection needs a file from this session where this app's code or config names the far end; for a part with no code here, its config, or the far side's code that takes its call, reads what it writes or writes what it reads | Before the check it says one line a connection, with its file, and an agent ends with such lines. Its last message names each app with the file that starts it |
| `flows` | A step is what a file showed in this session. It keeps each step's file and line as it reads, and holds the steps by them before the check | Its last message lists each step with its file and line |

**No record holds a path of the code, in any key**: both skills say so. The first run without
the key wrote the files into descriptions, on 7 of 8 apps and 5 of 27 connections.

## What is lost, as the owner was told

- **No warning when code moves.** Nothing in the tool knows where a part's code lies.
- **The proof is not kept.** Whether a connection was read or remembered can be told only by
  reading the code again. Counts such as "469 of 469 connections with a file" cannot be made.
- **No pointer into the code** for the next work: `flows` searches for a part's code by what
  the part is, and a mend of a model has nothing to start from.
- **What the rounds do and do not show.** In B a connection's file always stood in the
  record, as prose in round 2 and as the key after it: B does not show what the rule alone
  holds for a connection. C1 does for a step: with no key, 136 of 138 are shown in the code.

**Refused**: a key that names a copy of an app; a `name` that every step must have; a key for
a backend that is chosen or for one part that starts another; a key for a fork or for a loop.

**For the link, when it comes back**: a step's file is often not its connection's (at least 86
of 124 steps, by a rough count); one to three files fitted every step; a path can be right and
the record wrong; a mark for what is inferred belongs to the same design.

## Two reviews, and four runs

Astra and a Fable reviewer each read the removal apart. Neither found the key left in the
code, the check, the list, the page, the schema or the guide. Both found what the skills had
lost with it, and the texts now say it: the session keeps each app's folders for its agents,
and holds each connection in a message before the check.

| Run, on Syncthing | What it showed |
| --- | --- |
| `model`, the text as first cut | 27 connections, a clean check; the files went into descriptions |
| `model`, with "no record holds a path" | No path in any record; the connections were not held in sight |
| `model`, with "say in a message" | 9 apps, each named with the file that starts it; 29 connections, held in a message of 25 lines before the check; no path in any record |
| `flows`, on the second run's model | 10 steps, each listed with its file and line; 9 of 9 parts of the key in order; a clean check |

Asked afterwards, each run named the files behind its work, and its session had seen every one.

## What is not shown, and the tests

- **One system, one run a text**: none with several agents, on a large tree, or of a mend.
- 267 tests, eight fewer: ten that held the key are out; two are in, one that a part, a
  connection and a step with `source` are refused, one that keeps what the old file also held.
