# H1: A record of a repository

A stage after plan 3's six. Stage C2 took every link from a record to the code out, to come
back "with better understanding". Research and two proposals, Fable's and Astra's, were joined
on 2026-11-26 (`research/code-link/`, out of Git). This stage builds the one part the owner
then asked for: a record of a repository, with a flag for a workspace. The rest is not decided.

**After it** a model can say which repository holds a part's code. It never says where a
checkout lies on a machine. A skill that reads code knows which folder to read, and says by
name what it could not reach.

## Why a record, and why no path

- **A search in the wrong tree ends in "not found", which reads as "it is not so".** With a
  record a skill says: "I could not look: the code of `app-relay` is in `relay`".
- **A path on a disk** is true on one machine, names its user in a committed file, gives a
  session no access, and asks for a check that it is there: the old `source-gone`, a grain up.
- **A workspace is the case where a place is true on every machine**: one repository holds a
  script that clones the others as folders in it, each under its own name. There a flag says
  enough. In one such workspace of ten repositories, the earlier tool's records bear a path
  that is the name in 9 of 9.
- **And there a search from the root reads none of the code**: the workspace's ignore file
  names every member. Measured there: a search found 0 files from the root and 15 with one
  member's folder named. So the flag's words tell a skill to name the folder.

## The format's change

A seventeenth kind, `repositories`, after `technologies`: its id begins with `repo-`. It is a
thing that parts name and that no diagram draws, as an owner or a technology is.

| Key | Where | What it holds |
| --- | --- | --- |
| `name` (needed) | A repository | Its own name, as the folder of a plain clone bears it: one line of 1 to 100 characters, with no slash |
| `description` | A repository | What of the system lies in it, in 1 to 2,000 characters: the code of which parts, the deploy files, the documents |
| `url` | A repository | Where it is cloned from, as `https://…` or `git@…`: one line of 1 to 200 characters with no space. Never a path on a disk |
| `workspace` | A repository | `true`: on every machine its checkout lies beside the model's folder, in a folder of its `name`. Left out when its place differs from one machine to the next |
| `repository` | A system, an app | The id of the repository its code is in. Left out on an app, it is its system's. Left out on a system, it is the one the model's folder lies in, or nobody has said |

    # repositories/repo-shop-deploy.yaml
    name: shop-deploy
    description: The compose file and the scripts that start every app of the shop.
    url: https://example.org/tea/shop-deploy
    workspace: true

- **A record only for a repository other than the one the model's folder lies in.** A system
  whose code is all in that one has no record and no key.
- **One that no part names is no fault**: deploy files lie in one, and its `description` says so.
- **No folder inside a repository**, on a part or on the record: a folder is a claim about
  the code's inside, and the stage does not bring that back.
- **The guide carries the words a skill needs**: what `workspace` means for a search, and that
  a record is written from a file that names the repository or a person's word, never an image.

## What the check says

| What is held | Fault | Class |
| --- | --- | --- |
| The form of a repository | A key that is not its kind's; `name` with `/` or `\`, or `.` or `..`; `workspace` that is not `true` | error |
| `url` | It is a path on a disk: it begins with `/`, `\`, `~`, `.` or `file:`, or with a drive's letter and a colon. The mend says that where a checkout lies is never written | error |
| `repository` | It names no record of `repositories/`, or one of another kind; on a store, a component or another kind, "is not a key of" | error |

- **The check opens no folder but the model's.** It never looks whether a checkout is there,
  warns of no part without a repository, and counts nothing. A test holds that it says the
  same with a folder of that name beside the model and without one.
- **A team's rule never chooses a repository**: no selector names one, a rule judges none, and
  the count "Every record of the model" leaves them out.

## The command and the page

- **`seefore list`**: a repository's line ends with `workspace` where it bears the key. Under
  `--near`, a repository shows who names it under "named by:", and the apps that take it from
  their system under "through their system:"; an app that names none shows "its system's
  repository:".
- **`seefore guide repositories`** is a topic, and `seefore guide model` holds it.
- **`rename` and `remove`** treat the key as any id. **A change** may add, update and remove a
  repository, and `apply` writes it. **`init`** writes none.
- **The page**: a tab Repositories, after Owners. A repository's page shows its description,
  "URL" (a link only where it begins with `https://` or `http://`; the page fetches nothing),
  "Workspace" where it bears the key, and "Holds the code of": the systems and apps, with
  "from <the system>" where an app takes it. A system's or an app's page has a row
  "Repository". Nothing on the diagram, and no mark of whether a checkout is there.

## The skills

| Skill | What changes |
| --- | --- |
| `model` | Where the tree holds several repositories, it reads each in its own folder and names that folder in a search. It writes the repositories first, a record of each beyond the model's own, and names it on each system or app. Its text stays at 120 lines |
| `flows` | It finds a part's code in the folder of its repository and names that folder in each search. A repository it cannot read ends the trail, and it says which |
| `context`, `change`, `review`, `answer` | Nothing: they read no code. A change may add a repository as any record |

## What is not shown, what is out, and the tests

- **No run of a skill** was made for this stage: the two texts are changed and untried. Whether
  such a record helps a session is not measured anywhere: the benchmarks hand repositories over.
- **Out, and waiting for the owner**: a key for what a change read in the code; rules of
  reading printed by the tool; the design skills reading code. **Never**: a path, a folder, a
  branch or a commit in a record; a check that a checkout is there; a clone or any touch of Git.
- **Tests**: 338, ten of them new, one each. A repository in form and each fault with its
  mend; a rule that never chooses one; an app that takes its system's; the list's line and
  `--near` both ways; the guide's topic and its example as part of the one shop; the schema;
  `rename` and `remove`; a change that adds a repository and an app that names it, applied;
  the check with and without a folder beside the model; the pages.
