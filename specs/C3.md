# C3: Features, flows and data, read and checked

Stage C3 of `plan2.md`: the three new folders are read and checked. What a feature, a flow and
data are is in `specs/C1.md`, `specs/C2.md` and `specs/C2b.md`, all approved; this page says
what is built from them. The owner said to start it on 2026-11-24. Builder: Opus. Review:
Fable, the main session.

## What you can do after it

Write files in `features/`, `flows/` and `data/` of your model, run `seefore check`, and read
every problem in them: the file, the line and the column, what is wrong and how to mend it.
The page still opens such a model. It shows nothing of the three kinds yet: that is C4.

## What is in

- **Three kinds more**, twelve in all, each with its shape in `src/model/` and its JSON Schema
  in `schema/`, as the nine have. The new field names are `touches`, `starts`, `ends`,
  `feature`, `steps`, `fields`, and in a step `id`, `does`, `reply`, `after` and `data`.
- **A file in one of the three folders is read**, and gives the problems of one file (B1): a
  key not known, a key missing, a value of the wrong kind, an id not allowed. The warning for
  a folder that is not known no longer names these three.
- **A fault inside a step or a field has its own place**: the line and the column of the
  value at fault. Its message names it in words: "`does` of the third step".
- **The rules across records**, each with a sentence that says how to mend it:

| Rule | What must be true | Class | From |
| --- | --- | --- | --- |
| `id-twice` | The id of a feature, a flow or data is no other record's | error | B2 |
| `reference-unknown` | Each id in `touches`, `owner`, `feature`, and a step's `does` and `data`, names a record | error | B2 |
| `reference-wrong-kind` | `touches` names a part or a connection. `feature` names a feature. `does` names a connection, a part or a flow. `data` names data | error | B2 |
| `step-twice` | A step's id is used once in its flow | error | C2 |
| `step-shape` | Not both `does` and `reply`. A `name`, unless `does` names a flow or a connection that has a name. `data` only on a step that names a connection, or on a reply | error | C2, C2b |
| `step-earlier` | `reply` and `after` name earlier steps of this flow; `reply` one on a connection that does not end at a store | error | C2 |
| `flow-in-itself` | No flow runs itself, through any chain of steps | error | C2 |
| `feature-alone` | Some flow names the feature, or it touches something | count | C1 |
| `step-unplaced` | A step has `does` or `reply` | count | C2 |
| `record-unused` | Some step names each data record. An owner that a feature names is in use | count | B2 |

- **One fault is one problem**, as in B2. A step whose `does` names nothing gives that one
  problem and no other. A ring of flows that run each other is told once, and names each.
- **`seefore check`, with `--json`, and `/api/model`** give all of it, as they give the rest.

## Limits this page sets

The three pages say "a sentence" and "a name". The reader needs numbers:

| What | Limit |
| --- | --- |
| `starts`, `ends` | One line, 1 to 200 characters |
| A step's `name`, a field's `name` | As a record's `name`: one line, 1 to 100 characters |
| A step's `description`, a field's `description` | 1 to 300 characters |
| A step's `only` | As `only` on a record |
| A step's `id` | As a record's id. It is in no space but its flow's |

## What is out

- **Any list, page or highlight for the three kinds**: C4.
- **What is worked out from them**: a feature's parts, the data seen on a connection, the
  flows through a part. C4 builds these with the pages that show them.
- **A check that a flow is true**: a run with no problem says "no problem of form", as now.
- **A skill that writes them, and an index for agents**: milestone 8.

## Tests, about twelve

A small good model with one feature, one flow and one data record reads with no problem, and
`test/shop` gets them too. One test each for: a flow with no `feature`; a step with both
`does` and `reply`; a step with no name on a connection that has none; `data` on a step
inside a part; a step's id twice; a reply to a later step, and to a read of a store; a flow
that runs itself through another; `touches` that names an owner; `does` that names nothing,
with no second problem; a field's name twice. The three counts. The schemas of the three
kinds pass a good record and refuse a bad one.

## The try

The builder runs `seefore check` on a small model that holds the examples of the three pages,
and on broken copies of it. The main session then turns the 15 flows the explorers wrote, of
five systems, the private one among them, into this shape and checks them against their
models: every problem it finds is read, and none may be a fault of the checks.
