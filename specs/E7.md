# E7: Work that the tool lost

A stage after E6, from the same review (`research/review-2026-11-26/`, out of Git). Its
readers showed three ways in which `seefore remove`, `seefore apply`, `seefore rename` and the
skill `model` take away what a person has written. Fable and Astra planned the mend apart,
Fable tried it in a copy, and Astra, reading the trial, found three ways more. The owner
decided the two things that were open, on 2026-11-27. Built by the main session.

**After it** `remove` takes records of the model and nothing else, `apply` and `rename` look
at each new path before they write, a list of renames loses no file, and the skill `model`
stops where another skill's work names a record.

## What was wrong

| Case | Before | Now |
| --- | --- | --- |
| `seefore remove docker-compose deploy`, in a model at a project's root | Took `docker-compose.yml` and `k8s/deploy.yaml`: any YAML file under the folder, by its bare name | "there is no record" |
| `model` removes a stale record, is refused with "remove what names it in the same call", and calls `seefore remove person-clerk changes/orders-by-post reviews/orders-by-post` | Took the clerk, the open change and its review | The verb takes no change and no review; the skill has a sentence |
| `apply` adds a record, or `rename` moves one, where a link lies, or under a folder that is a link, or beside `App-New.yaml` on a disk that does not tell case apart | Wrote through the link to a file outside the model, or over the other file | Refused before anything is written |
| A list of renames: `x` to `b`, `b` to `c`, and a connection that follows its renamed end to `b` | Two records written to one file; one lost | The connection keeps its id, and the account says so |
| `seefore remove apps/app-test.yml`, where `apps/app-test.yaml` is there | Took the `.yaml` file | "there is no record" |
| `seefore remove` under a marker of another format, so that no record is read | Took a record that a connection names | Refused: the marker is mended first |

## `seefore remove`

- **A name finds only a YAML file directly in a folder of the model.** No other file under
  the model's folder is a record, whatever its name.
- **A change and a review are not removed**, by any name. A change ends when it is applied or
  rejected, and its review stays with it. A draft that nobody wants is deleted by hand. The
  owner agreed: this takes away something the verb did.
- **A name with no ending is a `.yaml` file; a name with its ending is that very file.** So
  `apps/app-odd.yml`, which the check faults, still goes by its whole name.
- **With a marker that does not read as format 1, nothing is removed**: nothing that names a
  record would be seen.
- **The hint follows what keeps the record.** A record names it: "remove what names it in the
  same call, or change it first", as before. An open change or its review does: "an open
  change or its review names it: decide the change first". A rule would break: the line says
  so, and no hint follows.

## The skill `model`

Step 1 says, of a mend: a record that is no longer true goes by `seefore remove <id>`, "and
only from a folder that step 4 names, with the records there that name it. Where it still
refuses, another skill's work names the record: touch neither, and say so at the end." So a
stale app goes with its own connections, and a flow, a rule, a line of context or a change
that names it keeps it. Two lines were won elsewhere; the skill has 120.

**`seefore remove` stays approved in advance**, as the owner said: "without asking". Astra
would have taken the approval out, since it covers any batch of records.

## `seefore apply` and `seefore rename`

- **Each path that must be new is looked at before the first write**, on a dry run too: the
  file of every record a change adds, and every path a rename moves a file to that no file
  of the same rename leaves. A refusal names each path and writes nothing.
- **The look goes part by part, by each folder's own list of names.** A link is refused, at
  the file or on the way to it; so is a part that is no folder.
- **A name that differs only by case is in the way, on every disk**: a model then never
  holds two names that another disk cannot, and the tests hold on Linux.
- **A new file is written only where nothing is** (`wx`), should one have come since the look.
- A file that is updated, rewritten or taken away was read as a file a moment before, and is
  written as before.

**A list of renames**: every id that a line leaves is freed before any id is taken. Two
files that would be written to one path are a refusal, whatever led there.

## What is out

- **An edit made while a verb runs**: Astra asked that each file be opened without following
  a link and held against what was read. Not built: it guards against another program alone.
- **A model whose own folder is a link** is read and written as before.
- **The check says nothing of a link it passes over**; the verb that would write there does.
- **An `apply` stopped half-way by the disk** still cannot go on.

## Tests, ten, and one changed

Eight in `test/writes.test.ts`: project YAML left alone; a change and its review; a name
with and without its ending; the marker; `apply` through three kinds of link; case, for a file
and a folder; a file that came after the look; the list of renames. One each for the files an
apply adds and for the skill's sentence. All ten fail on the code before. In
`test/rename.test.ts` a rule's break is no longer followed by a hint.

## The trial of the sentence

Six headless runs of `/seefore:model` on Opus, two a case, on a made-up bike rental of two
programs and a database whose model still holds a mailer that the code has no more
(`research/experiments/e7-remove/`, out of Git). 1.35 US dollars in all.

| The mailer is named by | What the runs did, both alike |
| --- | --- |
| Its own connection alone | Removed the connection, then the app |
| A step of a flow, on that connection | Asked to remove the connection, were refused with "remove what names it in the same call", and stopped: the app, the connection, the flow and the feature are as they were to the byte, and the last message says what stayed and why |
| An open change that updates the app | Removed the connection, which nothing else names; were refused the app; left the app and the change as they were, and said so |

- **No run removed or edited a flow, a feature or a change**, and none widened a call.
- **The bar was missed in its letter in the third case**: it asked that the connection stay
  too. The sentence does not ask that, and the app is then left with no connection, which
  the check counts and the last message tells.
- **Not shown**: the parallel join, a rule or a line of context that names the record, a
  change with a review, a system of real size, more than two runs a case.
