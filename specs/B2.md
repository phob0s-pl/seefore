# B2: Modelling rules

Stage B2 of `plan2.md`: what must be true across the records of a model, as checks. The rules
come from the check of the format in `research/modelling/` (out of Git) and from the changes
the owner agreed to on 2026-11-23, after Fable and Astra tried the rules on 52 small models of
patterns the trial systems do not have. The owner approved it on 2026-11-23. Builder: Sonnet.

## What you can do after it

Run `seefore check --workdir=<your model>` and read every problem: the file, the line, what
and the column, what is wrong and how to mend it. It ends with 1 when there is an error and
with 0 when there is none. `--json` gives the same as data, for an agent. The page shows the
same problems.

## Three classes

- **An error**: the model cannot be read right. It fails the run.
- **A warning**: the model can be read and says something doubtful. It never fails a run.
- **A count**: something left out or unused. It is no problem; the run only says how many.

A run with no problem says "no problem of form". It never says that the model is right.

## Every rule, on one page

| Id | What must be true | Class | How to mend it |
| --- | --- | --- | --- |
| `id-twice` | An id names one record in the whole model, whatever its folder | error | "Keep both records. Name the part for what it is for, and keep the product's name for the technology." |
| `reference-unknown` | Each id in `in`, `from`, `to`, `owner`, `technology` and `via` names a record | error | "No record has the id `go`. Write `technologies/go.yaml` with a `name`, or use an id that exists." It names the nearest id when one is close |
| `reference-wrong-kind` | An app is in a system; a component in an app; a piece of infrastructure in a system or in nothing; a store in a system or in the one app that keeps it, and never in a store. `from` and `to` name a person, a system, an app, a store, a component or a piece of infrastructure. `via` names a piece of infrastructure, an app, a component or a system. `owner` names an owner and `technology` technologies | error | A line for each case: "If it runs only inside the host, write it as a component of the host. If it runs on its own, put both apps in the system." "For our code inside somebody else's software, write that app inside the outside system and put the component in it." "A store is not passed through. Write one connection to it from each side." "Put both stores in the system. Name the server, or the table that holds the queue, in the description." |
| `access-not-store` | `access` stands only where `to` is a store | error | "If the far end holds the data, write that as a store in its system and end the connection there. If it is an API, say the read or write in the name." |
| `via-end` | No hop in `via` is itself an end of its connection. A hop may be in an end or hold one | warning | "Take `peer` out of `via`. If another copy passes it on, say which copy in the name." |
| `connection-twice` | No two named connections agree in every field | warning | "If they are one exchange, keep one. If they are two, tell them apart by name, `via` or `only`." |
| `record-unused` | Some record names each owner and each technology | count | "Nothing names `valkey`. Keep it if it is listed on purpose; else remove its file." |

- **One fault is one problem.** A clash of ids is reported once and names every file.
- **No follow-on errors.** A record whose file is broken still stands for its id, and a
  reference to an id that two files claim is not reported again.
- **A count is given only when every file was read.** Otherwise it says "not counted".
- **`opens` may stand on any connection**, also where `to` is a store, beside `access`.
- **A connection may start at a store.** A store's own service may deliver, and code in a
  store may call out. The convention below says when; no rule checks it.
- **A place has a column** beside its line, in every problem, those of B1 too.
- **No rule asks for an owner, a technology or a description.**

## Who acts, with a store

The spec carries this for whoever writes a model; no rule can hold it.

- **A poll or a read** points at the store, from the one that reads.
- **A wake-up followed by a read** is drawn as the read; the name says what starts it.
- **A delivery to an endpoint that never reads the store** points at the receiver: from the
  sender if it is known, and from the store if the store's own service delivers.

## What is in

- **The rules, in `src/model/`**, with no AI and no disk. A rule has an id, a class, one
  sentence that says what must be true, and a check. A check names a record and a field; one
  place turns that into a file and a line. The model answers what a rule asks: the record
  of an id, its kind, what it is in, what is in it, and the connections that touch it.
- **`/api/model`** gives the problems of the rules with those of B1, and the counts apart.
- **The page** lists them the same way, with the counts after the problems.
- **`seefore check`**, with `--workdir` and `--json`.

## What is out

- **The other rules of the proposal**: a store an app keeps that others reach, a connection
  repeated higher up, a vague name, the counts of what is left out. They come at B4 and B5.
- **Gone for good**: `store-acts`, `opens-at-store`, `passes-on-only`, `broker-as-store`.
- **Waiving a rule, and a team's own rules**: milestone 6. **A page of the rules**: B5.

## An example

    $ seefore check --workdir=models/shop
    stores/jobs.yaml:2:5: error: `in` names `orders`, which is a store. A store is never in a store.
      Mend: Put both stores in the system. Name the server, or the table that holds the queue, in the description.

    13 records read. 1 error, 0 warnings. 2 owners or technologies that nothing names.

## Tests, about twelve

One for each rule, with a small model that breaks it and one that does not. A broken file
gives no follow-on error. `seefore check` ends with 1 on an error and with 0 on a warning
alone, and `--json` gives the problems as data.

## The try

On all eight trial models: no error and no warning. On the 52 small models of other
patterns: none that tells the truth fails for a rule this page changed.

## Choices, as approved

1. **`store-acts` is dropped as a check.** Who acts with a store is a convention.
2. **"No store in a store" is a case of `reference-wrong-kind`**, with a fix of its own.
3. **A place has a column.**
4. **`seefore check` has `--json`** from the start, since agents are its first users.
